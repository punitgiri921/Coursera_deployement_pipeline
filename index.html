BUCKET 1 Foundation, Workspace Topology & Consumption Design
Topology • RBAC • Storage Modes • Apps
1. Workspace Segregation & Cardinality:
  • Dev Isolation (CL-07): Independent Dev workspaces isolate sprint cadences (e.g. weekly sales vs monthly financial close), prevent simultaneous .pbix publish collisions, and protect sensitive domain data during active development.
  • 1:1 Stage Cardinality (CL-05): Power BI native Deployment Pipelines enforce a strict 1:1 workspace mapping per stage (Dev -> Test -> Prod). Multi-team parallel development is handled via domain-specific pipelines or Git branching.
2. Access Governance & Separation of Duties:
  • Least-Privilege RBAC (CL-15): Developers hold Contributor/Member roles in Dev, Viewer in Test, and No Direct Access (or Viewer) in Production.
  • Production Distribution Standard (CL-06): End users access production solely through a published Power BI App with audience-level targeting, never direct workspace membership.
3. Artifact Lifecycle & Storage Mechanics:
  • Artifact Dependency (CL-02): Report visuals bind strictly to the underlying semantic model schema. Deploying a report without its updated dataset causes visual breakage ('Field Not Found').
  • Import Cache Lifecycle (CL-09, CL-29): Deployment pipelines transfer model definitions and schema metadata only. The cached VertiPaq data rows are never copied across stages (Dev: 605 rows -> Test: 0 rows initially).
BUCKET 2 Model Engineering, PBIP / TMDL & CI/CD Quality Gates
Source Control • PR Governance • Tabular Editor BPA
1. Source Control & Text Serialization:
  • Git vs Pipeline Separation (CL-03): Git tracks text definitions, version history, and branching; Deployment Pipelines manage stage assignments, environment swapping, and runtime promotion.
  • TMDL & PBIP Serialization (CL-21): Power BI Project (.pbip) format breaks monolithic binary models into individual, human-readable text files per table, measure, and partition (.tmdl), enabling clean line-by-line diffs.
2. Multi-Team Branching Strategy:
  • Shared Core Model Collaboration (CL-16): Developers work in dedicated feature branches (feature/finance, feature/sales), validate changes via Pull Requests (PRs), and merge into main to prevent unresolvable binary merge conflicts.
3. Automated Code Quality & Linting Gates:
  • PR Code Review (CL-22): Peer inspection validates M query parameterization, DAX measure logic, and schema regressions before merging into main.
  • Automated CI with Tabular Editor BPA (CL-23): GitHub Actions runs TabularEditor.exe /analyze to enforce 50+ Best Practice Analyzer rules (e.g. formatting DAX, hiding foreign keys, requiring descriptions), automatically blocking PRs on technical debt.
  • TMSL / BIM Schema Diff (CL-10, CL-20): Pipeline comparison engines evaluate JSON/TMSL metadata across stages, displaying divergence badges and exact item differences before promotion.
BUCKET 3 Power Query Parameterization & Deployment Rules
Decoupling • Target Stage Binding • Schema Parity
1. Environment Decoupling:
  • Decoupling Risk (CL-04): Models deployed without parameters or rules remain connected to upstream Dev/Test sources, exposing test data in Production.
  • Parameter Target (CL-08): Defining Power Query parameters (p_ServerName, p_DatabaseName, p_FilePath) enables pipeline deployment rules to swap connections dynamically during promotion.
2. Deployment Rules Configuration Flow:
  • Target-Stage Rule Configuration (CL-11): Rules are configured on the target stage (Test / Prod), not the source. The promotion engine intercepts parameters and swaps values before saving to the target workspace.
  • Initial Deployment Precondition (CL-12): Rules cannot be configured on an empty stage. The initial deployment establishes the dataset definition; subsequent rule configuration persists for all future promotions.
  • Rule Divergence Badge (CL-13): When a deployment rule is active, the dataset displays an orange "Different from source" indicator, confirming active parameter divergence.
3. Defensive Power Query Architecture:
  • Schema Drift Resilience (CL-25): If downstream environments alter sheet names or table structures, hardcoded navigation ([Item="Sales_2026"]) crashes refresh. Models must maintain schema parity or use defensive indexing (Source{0}[Data]).
BUCKET 4 Pipeline Promotion, Refresh & Gateway Infrastructure
Execution • Cache Hydration • HA Gateways • REST APIs
1. Deployment vs Refresh Execution:
  • Deployment Moves Model, Refresh Loads Data (CL-19, CL-29): Data refresh updates rows from the connected source according to the cloud schema; it cannot pull new measures/columns from local Desktop files without a new deployment/publish.
  • Two Mandatory Target Configurations (CL-30): (1) Parameter Deployment Rules: Bind dataset to target connection; (2) Authenticated Refresh & Credentials: Configure Gateway / OAuth2 credentials and trigger post-deployment refresh to populate the VertiPaq cache.
DEV (605 rows) ──[Deploy via Pipeline (Schema Only)]──> TEST (0 rows) ──[Authenticated Refresh]──> TEST (600 rows)
2. Gateway Infrastructure & Cloud Modernization:
  • Gateway Requirements (CL-01): Cloud compute (Power BI Service) cannot reach local file paths (D:\...) without an On-Premises Data Gateway.
  • HA Clusters & Cloud-Native Storage (CL-26): Eliminate gateway failure points by deploying High-Availability Gateway Clusters or migrating files to cloud storage (SharePoint Online, Azure SQL, OneLake) for direct cloud-to-cloud OAuth2 refresh.
3. Automated CI/CD Execution:
  • Fabric REST API & Service Principals (CL-24): GitHub Actions executes POST /v1/workspaces/.../deployStage via Azure Entra ID Service Principals, enforcing zero developer production access and deterministic automated deployments (Deploy -> Refresh -> Smoke Test Query).
BUCKET 5 Security, Compliance, Auditing & Governance
RLS • Freeze Windows • Dual Audit Trails • Master Blueprint
1. Security Lifecycle:
  • Row-Level Security (RLS) Propagation (CL-14): RLS DAX rules deploy automatically with the model schema. User and Entra security group memberships must be mapped per workspace/dataset in Power BI Service.
2. Freeze Windows & Dual Auditability:
  • Production Freeze Windows (CL-18): Enforced during financial close periods by revoking stage deployment permissions or locking CI/CD Service Principal pipeline triggers.
  • Dual Audit Trails (CL-17): Git Commit History provides cryptographic, line-by-line proof of exact TMDL DAX and M query changes; Deployment Pipeline History provides an environment-level record of deployer identity, timestamp, items deployed, and change ticket notes.
  • Master Blueprint Synthesis (CL-28): Integrates Multi-Team Git authoring, Regulatory Compliance role locks, and Sandbox 3-Gate graduation into a single enterprise governance standard.
BUCKET 6 Validation, Rollback & Incident Recovery
Forward-Only Pipelines • Git Revert • Cache Invalidation
1. Pipeline Limitations & Git Recovery:
  • Forward-Only Pipeline Limitation (CL-27): Deployment pipelines do not store historical snapshots and offer no UI rollback button.
2. Step-by-Step Rollback Workflow (CL-27, CL-30):
  • Step 1: Run git revert <commit-sha> on the PBIP / TMDL branch.
  • Step 2: Merge the revert PR into main (synchronizing the Dev workspace).
  • Step 3: Fast-forward promote the restored model through the pipeline (Dev -> Test -> Prod).
  • Step 4 (Cache Invalidation): Trigger an immediate post-rollback Data Refresh in Production to purge corrupt VertiPaq cache and recalculate visuals before reopening user access.

Troubleshooting Knowledge Base Failure Injection & Mitigation Log
TB-01 Visuals Error / Empty Data in Test/Prod after Pipeline Promotion
Resolved & Documented
Root Cause Analysis (RCA):
  • • Import Cache Behavior: Deployment pipelines copy schema & metadata only; cached VertiPaq table rows are NOT transferred downstream.
  • • Empty Semantic Model: Downstream models contain 0 rows until refreshed.
  • • Local Gateway Barrier: Local paths (D:\...) in parameters require an On-Premises Data Gateway to refresh in cloud service.
Production Remediation & Fix:
  • • Store enterprise datasets in Cloud Storage (SharePoint Online / OneLake / ADLS Gen2 / Azure SQL) for native cloud refresh.
  • • For local files, configure an active On-Premises Gateway.
  • • Always trigger an immediate post-deployment refresh on target stages.
Governance & Prevention Gate: Include mandatory Gate 2 (Post-Deployment Refresh & Gateway Check) in the deployment validation checklist before releasing reports to business users.
TB-02 New Column/Measure in Desktop Not Appearing after Cloud Data Refresh
Resolved & Documented
Root Cause Analysis (RCA):
  • • Schema vs Data Refresh: Cloud data refresh extracts updated data rows for the existing cloud schema only. It does not monitor local .pbix files or alter dataset metadata.
  • • Saved vs Published: Saving in Desktop only updates the local file on disk; it does not deploy model schema to Power BI Service.
Production Remediation & Fix:
  • • Click Publish in Power BI Desktop to upload the new schema to finanance_dev.
  • • Open Deployment Pipeline → confirm orange comparison indicator → deploy to Test and Prod.
Architectural Rule: Differentiate between Schema Changes (require Publish / Git PR) and Data Changes (require Data Refresh).
TB-03 Downstream Refresh Failure: 'The key didn't match any rows in the table'
Resolved & Documented
Root Cause Analysis (RCA):
  • • Environment Schema Drift: Parameterized deployment redirected dataset to the Test/Prod source, but the sheet name (e.g. Sales_2026) or table structure in the Test/Prod file did not match the hardcoded M navigation key.
  • • Desktop False Confidence: It worked on Desktop because the developer's local Dev workbook had the new sheet name, while the Test environment source had not been updated.
Production Remediation & Fix:
  • • Schema Parity: Align the Test/Prod source file schema (sheet/table names) with the model contract.
  • • Defensive Power Query: Refactor M code to use dynamic indexing (Source{0}[Data]) instead of hardcoded key lookup.
  • • CI Pre-Flight Checks: Run automated schema validation against target test databases before promotion.
Architectural Rule: Environment parameters decouple connection paths, but schema parity across physical sources must be strictly guaranteed.
TB-04 Gateway Timeout & Credential Expiration: DM_GWPipeline_Gateway_InvalidConnectionCredentials
Resolved & Documented
Root Cause Analysis (RCA):
  • • Gateway VM Offline/Asleep: Host machine running the Gateway service was powered down, entered sleep/hibernation, or lost network connection.
  • • Expired Credentials: Windows account, database login, or service account password expired or was reset without updating the cloud gateway connection settings.
Production Remediation & Fix:
  • • High Availability (HA) Clusters: Deploy gateway clusters across 2+ dedicated Azure VMs with auto-failover and load balancing.
  • • Service Principal Authentication: Use Azure Entra ID Service Principals with Managed Identities and non-expiring client secrets for database connections.
  • • Cloud Storage Migration: Modernize on-prem files to SharePoint Online / OneLake / ADLS Gen2 for direct, gateway-less cloud refreshes.
Architectural Standard: Eliminate single points of failure by implementing HA Gateway Clusters and migrating enterprise storage to cloud-native repositories.

2. Enforcing Regulatory Freeze Windows

During quarter-end financial closes (e.g. Q4 close):
• Role De-elevation: Temporarily revoke stage deployment permissions on the Test -> Prod pipeline stage.
• Automated Pipeline Lock: Disable production deployment triggers in GitHub Actions / Fabric REST API during the freeze window.
• Result: Developers can fix bugs in Dev, but no changes can physically reach Prod until the freeze is lifted.

3. Dual Audit Trails

• Git Commit & PR History: Line-by-line proof of exact TMDL formula changes, M parameter updates, and committer identity.
• Deployment Pipeline History: Environment-level record showing deployer email, timestamp, target stage, item count, and deployment note (e.g. "Release v2.4 approved by CFO under CR-9042").
